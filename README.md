# Крепости

Стратегия для Telegram Mini App (Phaser + TypeScript). Описание проекта и принципы — в [claude.md](claude.md).

## Структура

- `client/` — игра: Vite + TypeScript + Phaser 4.
  - `src/platform/` — единственное место, где есть Telegram (TelegramPlatform) и тестовый игрок для браузера (BrowserPlatform).
  - `src/api/` — HTTP-клиент игрового API (JWT хранится только в памяти).
  - `src/game/` — сцены, изометрия, тема; `src/game/battle/` — бой: контроллер (поиск, живой бой на движке из shared, итог от сервера), сцена поля и интерфейс боя.
  - `src/i18n/` — тексты ru/en.
- `server/` — API на Fastify + PostgreSQL.
  - `migrations/` — SQL-миграции, применяются по порядку имён.
  - `src/telegram/initData.ts` — проверка подписи Telegram initData.
  - `src/players.ts` — вход и создание игрока (из игры и из бота); `src/game.ts` — игровые действия в транзакциях.
  - `src/battles/` — протокол боя (`actions.ts`) и подсчёт итога сервером (`close.ts`).
  - `src/bot/` — бот на grammY: команды, настройки, webhook/long polling.
  - `src/notifications/` — очередь уведомлений: план (`plan.ts`), правила частоты и тихие часы (`policy.ts`, `timing.ts`), таблица (`store.ts`), воркер (`worker.ts`), тексты (`messages.ts`).
  - `src/i18n/` — тексты бота и уведомлений ru/en (варианты фраз чередуются).
  - `src/events.ts` — события для статистики удержания.
- `shared/` — общий код клиента и сервера:
  - `balance.ts` — **все игровые числа экономики**: стоимость, время, требования ратуши, HP, добыча и вместимость по уровням, хранилище и лимиты ратуши, число строителей;
  - `economy.ts` — правила экономики чистыми функциями от «текущего времени»: накопление, сбор, завершение стройки, проверки постройки и улучшения;
  - `troops.ts` — **войска по уровням** (стоимость, время тренировки, место в армии, HP, урон, скорость атаки, радиус, скорость, приоритет целей) и место в армии по уровню казармы;
  - `army.ts` — правила казармы: очередь тренировки, отмена, место в армии;
  - `battle/` — детерминированный движок боя (`simulate`), его числа (`config.ts`: башня, зона высадки, добыча, лимит времени, цена поиска), A* (`path.ts`), формат базы для боя (`types.ts`, `snapshot.ts`), базы-боты (`bots.ts`), проверка высадок игрока (`orders.ts`);
  - `base.ts` — размещение на поле (`checkPlacement`); `buildings.ts` — типы и размеры зданий; `api.ts` — типы запросов и ответов API.

## Первый запуск

Нужны Node.js 22+ и Docker.

```bash
npm install
cp server/.env.example server/.env   # и задать JWT_SECRET: openssl rand -hex 32
npm run db:up                        # Postgres в Docker на localhost:5433
npm run db:migrate                   # создать таблицы
npm run dev                          # сервер на :3000 и клиент на http://localhost:5173
```

Откройте http://localhost:5173 — войдёт тестовый игрок, база загрузится с сервера.

## Команды

```bash
npm run dev          # сервер и клиент вместе
npm run dev:server   # только сервер (перезапускается при изменениях)
npm run dev:client   # только клиент
npm run db:up        # поднять Postgres (docker compose)
npm run db:down      # остановить Postgres (данные сохраняются в volume)
npm run db:migrate   # применить новые миграции
npm test             # тесты shared и server (серверные — на базе forts_test, нужен npm run db:up)
npm run typecheck    # проверка типов во всех пакетах
npm run build        # проверка типов + сборка клиента в client/dist
npm run build:server # сборка server + shared в JavaScript (server/dist)
npm run start:server # запуск собранного сервера: миграции, затем приём запросов
```

Сбросить базу полностью: `docker compose down -v`, затем `npm run db:up && npm run db:migrate`.

Если порт 5433 занят: `FORTS_DB_PORT=5434 npm run db:up` и тот же порт в `DATABASE_URL`.

## Настройки

`server/.env` (образец — `server/.env.example`), проверяется при старте, при ошибке сервер не запустится:

| Переменная | Назначение |
|---|---|
| `NODE_ENV` | `development`, `production` или `test` |
| `BOT_TOKEN` | токен бота от @BotFather — ключ для проверки initData |
| `DATABASE_URL` | строка подключения к Postgres |
| `JWT_SECRET` | секрет для JWT, не короче 32 символов |
| `CORS_ORIGIN` | адреса клиента через запятую |
| `HOST`, `PORT` | необязательно, по умолчанию `0.0.0.0:3000` |
| `WEBAPP_URL` | https-адрес мини-приложения для кнопок бота; обязателен в production, локально — по желанию |
| `PUBLIC_URL` | только production: публичный https-адрес сервера, webhook ставится на `<PUBLIC_URL>/telegram/webhook` |
| `WEBHOOK_SECRET` | только production: секрет заголовка `X-Telegram-Bot-Api-Secret-Token`, 16–256 символов `A-Za-z0-9_-` (`openssl rand -hex 32`) |
| `NOTIFY_TEST_MODE` | `1` — короткие задержки уведомлений для ручной проверки; работает только при `NODE_ENV=development` |

`client/.env` (образец — `client/.env.example`): `VITE_API_URL` — адрес API. В режиме разработки по умолчанию `http://localhost:3000`, для сборки обязателен.

## Деплой сервера на Railway

Сервис собирается из корня монорепозитория (Root Directory не задаётся). Команды уже описаны в [railway.json](railway.json), Railway подхватит их сам:

- Build Command: `npm run build:server` — esbuild собирает `server/src` вместе с `shared` в `server/dist`;
- Start Command: `npm run start:server` — `node server/dist/index.js` без tsx;
- Healthcheck Path: `/health`.

Сборщик (esbuild) лежит в `dependencies` сервера, поэтому сборка работает и при `NODE_ENV=production`, когда npm не ставит devDependencies. Проверка типов в сборку не входит — запускайте `npm run typecheck` перед пушем.

Настройка:

1. New Project → Deploy from GitHub repo → выбрать этот репозиторий.
2. В проекте: New → Database → PostgreSQL.
3. В сервисе сервера → Variables:
   | Переменная | Значение |
   |---|---|
   | `NODE_ENV` | `production` |
   | `DATABASE_URL` | `${{Postgres.DATABASE_URL}}` (ссылка на базу из шага 2) |
   | `BOT_TOKEN` | токен бота от @BotFather |
   | `JWT_SECRET` | новый ключ: `openssl rand -hex 32` (не тот, что локально) |
   | `CORS_ORIGIN` | адрес клиента на Vercel, например `https://forts.vercel.app` |
   | `PORT` | `3000` |
   | `WEBAPP_URL` | адрес клиента на Vercel — для кнопок и меню бота |
   | `PUBLIC_URL` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` (домен из шага 4) |
   | `WEBHOOK_SECRET` | новый ключ: `openssl rand -hex 32` |

   Сервер слушает `0.0.0.0` на порту из `PORT`.
4. Settings → Networking → Generate Domain → на вопрос о порте указать `3000` (тот же, что в `PORT`) — получить публичный адрес API.
5. На Vercel в переменных клиента указать `VITE_API_URL=https://<домен из шага 4>` и пересобрать клиент.

Миграции применяются автоматически при каждом старте сервера до приёма запросов; уже применённые пропускаются. Вход тестового игрока (`/auth/dev`) в production отключён.

Бот запускается в том же сервисе. При старте сервер сам задаёт команды, описания (ru/en), кнопку меню с мини-приложением и ставит webhook на `PUBLIC_URL/telegram/webhook` с `WEBHOOK_SECRET` — в @BotFather ничего настраивать не нужно. Проверить: `curl https://api.telegram.org/bot<токен>/getWebhookInfo`. Если экземпляров несколько, воркер уведомлений безопасен: каждый игрок обрабатывается под блокировкой `FOR UPDATE SKIP LOCKED`.

**Не запускайте локальный сервер с токеном боевого бота**: в development он переходит на long polling и снимает webhook. Для локальной разработки заведите отдельного тестового бота.

## API

Типы всех запросов и ответов — в `shared/src/api.ts`. Ошибки приходят как `{ "error": "<код>", "message": "..." }`.

| Запрос | Что делает |
|---|---|
| `POST /auth/telegram` `{ initData }` | проверяет подпись и возраст (≤ 24 ч), создаёт игрока при первом входе, возвращает JWT |
| `POST /auth/dev` `{ devId, name, languageCode }` | вход тестового игрока; существует **только** при `NODE_ENV=development` |
| `GET /me` | состояние базы: игрок, ресурсы, здания, `serverTime` |
| `POST /buildings` `{ type, x, y }` | поставить здание: место, уровень ратуши, лимит, свободный строитель, ресурсы |
| `POST /buildings/:id/upgrade` | начать улучшение до следующего уровня |
| `POST /buildings/:id/collect` | забрать накопленное из шахты/фермы, не больше свободного места в хранилище |
| `POST /buildings/:id/move` `{ x, y }` | перенести здание, бесплатно |
| `POST /army/train` `{ troop, count }` | заказать юниты: нужна казарма нужного уровня, место в армии и еда |
| `POST /army/queue/:id/cancel` | отменить юнит из очереди, еда возвращается |
| `POST /battles/search` `{ next }` | цель для атаки: превью базы и возможная добыча; `next: true` — другая цель за золото |
| `POST /battles/start` | начать бой с найденной целью: `battle.id`, база, `seed`, армия на начало |
| `POST /battles/:id/deployments` `{ deployments }` | высадки по ходу боя (полный список) — сервер применит их, если итог не придёт |
| `POST /battles/:id/finish` `{ deployments, endTick }` | итог: сервер проверяет высадки, сам считает бой и применяет результат |
| `POST /notifications/write-access` `{ granted }` | ответ на предложение уведомлений в игре |
| `POST /telegram/webhook` | обновления бота от Telegram (только production, с секретным заголовком) |

Вход (`/auth/telegram`, `/auth/dev`) дополнительно принимает `timezone` (IANA) и `startParam` (параметр запуска из адреса кнопки; подписанный `start_param` из initData важнее).

Все игровые запросы отвечают полным состоянием базы (`BaseSnapshot`), клиент просто заменяет им своё. Отказ по правилам игры — `422` с кодом (`not_enough_resources`, `no_free_builder`, `townhall_level_too_low`, `limit_reached`, `under_construction`, `max_level`, `storage_full`, `no_barracks`, `barracks_level_too_low`, `army_full`, …).

Все запросы, кроме входа, требуют заголовок `Authorization: Bearer <token>`.

### Как устроена экономика

- Фоновых таймеров и cron нет. У здания хранится `finish_at` (до какого момента идёт стройка/улучшение), `collected_at` и `stored` (с какого момента и с какого остатка идёт добыча). Всё остальное вычисляется при запросе функциями из `shared/src/economy.ts` с параметром «текущее время».
- Стройка завершается при первом запросе после `finish_at`: уровень +1, добыча начинается ровно с `finish_at`. Пока здание строится или улучшается, добыча стоит.
- Каждое действие выполняется в транзакции с блокировкой строки игрока, поэтому запросы одного игрока идут строго по очереди: двойной тап «Улучшить» улучшит и спишет один раз, двойной сбор начислит один раз. Клиент вдобавок не отправляет повторный запрос, пока первый в пути.
- Клиент показывает таймеры и накопленное по времени сервера: из каждого ответа берётся `serverTime` и поправка на разницу часов. Когда таймер доходит до нуля, клиент перезапрашивает базу.

### Казарма и армия

- Очередь тренировки одна на игрока, юниты тренируются по одному: `finish_at` каждого — за предыдущим. Готовые переходят в армию при первом запросе после `finish_at` (как стройки, без cron).
- Место в армии — сумма по всем казармам (`BARRACKS_CAPACITY` по уровню); занимают и готовые юниты, и очередь. Уровень тренируемых юнитов задаёт лучшая казарма.
- Отмена возвращает всю еду, следующие юниты становятся готовы раньше на оставшееся время отменённого.

### Как устроен бой

`simulate(base, deployments, seed, untilTick?, { log })` в `shared/src/battle/` — чистая функция: один и тот же вход даёт один и тот же результат на сервере и в клиенте (сервер пересчитывает бой и не верит клиенту).

- 10 тиков в секунду, не дольше 3 минут. Только целые числа: длина в «единицах» (клетка = 1000), время в тиках, случайность — свой PRNG из `seed`. Здания обходятся по id, юниты — по номеру высадки.
- `base` (`BattleBase`) — единый формат базы для ботов и игроков: размер поля, ресурсы в хранилище, здания с уровнями и накопленным в шахтах. Настоящую базу переводит `battleBaseFromPlayer`.
- Поле боя шире базы на 4 клетки с каждой стороны. Высадка — на клетку не ближе 2 клеток к любому зданию; иначе `forbidden_zone`.
- Путь — A* по клеткам с кэшем. Вход в клетку стены стоит `wallDetourTiles` лишних клеток: если обход не намного длиннее — юнит обходит, иначе ломает стену. Таран сначала бьёт оборону, потом стены.
- Башня бьёт ближайший юнит в радиусе. Стены только держат удар и перекрывают проход.
- Результат: % разрушения (без стен), звёзды (50%, ратуша, 100%), добыча (доля хранилища — поровну по зданиям по мере разрушения, плюс доля накопленного в разрушенных шахтах/фермах), потраченные и выжившие войска, итоговый тик и хэш состояния.

### Бой с базой-ботом

- **Цели.** 12 шаблонов баз для ратуши 1–5 (`shared/src/battle/bots.ts`, карта 12×12 буквами). Генератор по seed поворачивает/отражает шаблон, иногда понижает уровни зданий и разбрасывает ресурсы. Подбор — ратуша ±1 от атакующего; первый поиск бесплатный, «Следующая» стоит золота (`SEARCH_COST_GOLD`).
- **Протокол.** `search` → `start` (сервер записывает время начала, базу, seed и армию на начало) → по ходу боя `deployments` → `finish`. У игрока одновременно одна найденная цель или один бой (уникальный индекс в `battles`).
- **Высадка** от клиента — `{ tick, troop, x, y }`, без уровня: уровень берётся из армии на начало боя (сначала старшие), одинаково у клиента и сервера.
- **Проверки сервера:** войска есть в армии на начало, тики целые, не убывают и меньше конца боя, клетки в разрешённой зоне, уже присланные высадки не меняются, реальное время с начала не меньше, чем прошло тиков (с запасом 2 с на сеть).
- **Итог считает только сервер** (`simulate` по сохранённым данным): списывает высаженные войска, начисляет добычу не больше свободного места в хранилище. Повторный `finish` возвращает тот же итог и ничего не начисляет. Если высажена вся армия, бой кончается гибелью последнего юнита; иначе — сдачей («Завершить»), 100% или по времени.
- **Без итога за 5 минут** бой закрывается при следующем запросе игрока (без cron) с теми высадками, что сервер знает; нет высадок — поражение без потерь. Новый поиск тоже закрывает брошенный бой.
- **Бои хранятся** в `battles`: база, seed, армия на начало, высадки, тик конца, итог — для повторов и будущей мести.
- **Клиент** ведёт бой тем же движком (`createBattle` + `addDeployment` + `stepBattle`, 10 тиков в секунду), рисует с интерполяцией между тиками, а экран итога показывает ответ сервера. Если хэш сервера разошёлся с клиентским, в консоли будет предупреждение.

### Как проверить бой

1. `npm run db:migrate`, `npm run dev`, открыть http://localhost:5173.
2. Построить казарму (200 еды, 20 с), тап по ней → обучить войска (воин — с казармы 1, лучник — 2, таран — 3).
3. «⚔ В бой» → превью цели и возможная добыча; «Следующая» — другая цель за золото.
4. «Атаковать» → выбрать войско внизу, коснуться поля у края (зажатие — несколько юнитов подряд). Тап у зданий подсветит красную запрещённую зону. Щипок / колесо — масштаб.
5. Дождаться конца или нажать «Завершить» → итог от сервера; «Домой» — ресурсы и армия уже обновлены.

## Тестовый игрок в браузере

Вне Telegram клиент входит через `/auth/dev`, игрока можно настроить через URL:

- `?id=42` — номер тестового игрока, у каждого своя база (по умолчанию 1);
- `?lang=en` / `?lang=ru` — язык (по умолчанию язык браузера);
- `?name=Вася` — имя.

Тема берётся из системной настройки (светлая/тёмная).

## Запуск внутри Telegram

1. В `server/.env` указать настоящий `BOT_TOKEN` вашего бота.
2. Создать `client/.env` с `VITE_API_URL=/api` — запросы пойдут через dev-сервер Vite, и хватит одного туннеля.
3. `npm run dev` и туннель с HTTPS на клиент: `cloudflared tunnel --url http://localhost:5173` или `ngrok http 5173`.
4. В @BotFather: `/newapp` (или Menu Button у бота) — указать URL туннеля.
5. Открыть мини-приложение в Telegram. Платформа определяется автоматически по параметрам запуска (`#tgWebAppData`).

## Бот и уведомления

Команды: `/start` (приветствие и кнопка «Играть»; параметр `/start <источник>` запоминается как источник прихода), `/settings` (вкл/выкл уведомлений по типам), `/help`.

Бот может писать игроку, если тот нажал `/start`, разрешил сообщения в мини-приложении (`allows_write_to_pm` в initData) или согласился на предложение в игре: после первой постройки игра один раз спрашивает «Присылать уведомления, когда постройка готова?» и вызывает системный запрос Telegram. Отказ запоминается, повторно — не чаще раза в неделю.

Уведомления:

- `build_done` — стройка/улучшение завершены;
- `storage_full` — шахты (ферма) заполнились; одно на тип ресурса;
- `army_ready` — дотренирован последний юнит в очереди казармы.

Как устроено:

- После каждого игрового запроса сервер пересчитывает план (`notifications/plan.ts`) и приводит к нему таблицу `notifications`: одна строка на (игрок, тип, объект). Новое время события — строка снова `pending`; уже отправленное событие повторно не отправляется; пропавшее из плана (игрок собрал ресурсы) — `cancelled`.
- Воркер в том же процессе раз в 30 с берёт игроков с созревшими уведомлениями, пересчитывает план по текущей базе (неактуальное отменяется) и проверяет правила: игрок не заходил последние 2 минуты; не больше 4 сообщений в сутки и не чаще раза в 30 минут; тихие часы 23:00–08:00 по часовому поясу игрока (клиент передаёт его при входе) — отложенное уходит утром. События в пределах 10 минут объединяются в одно сообщение.
- 403 от Telegram — `can_message = false` до следующего `/start`; 429 — ждём `retry_after`; прочие ошибки — до 3 попыток.
- Кнопка «Открыть крепость» открывает игру с `?startapp=notif_<тип>` — вход по уведомлению попадает в статистику.

Статистика — таблица `events`: `login`, `notification_sent`, `notification_open`, `bot_start`, `write_access`. Например, сколько входов по уведомлениям за неделю:

```sql
SELECT date_trunc('day', created_at) AS day,
       count(*) FILTER (WHERE type = 'notification_sent') AS sent,
       count(*) FILTER (WHERE type = 'notification_open') AS opened
FROM events WHERE created_at > now() - interval '7 days'
GROUP BY 1 ORDER BY 1;
```

### Ручная проверка уведомлений локально (без туннеля)

1. В `server/.env`: `BOT_TOKEN` **тестового** бота и `NOTIFY_TEST_MODE=1` (задержки: «в игре» — 15 с, между сообщениями — 1 мин, объединение — 20 с, воркер — каждые 5 с; тихие часы действуют как обычно).
2. `npm run dev`, написать боту `/start`. В режиме разработки бот ответит ссылкой вида `http://localhost:5173/?tgid=<ваш id>` — это вход в игру тем же игроком.
3. Открыть ссылку, построить шахту (10 с) и закрыть вкладку. Примерно через 15–20 с придёт «Шахта построена». Через 1 мин после неё — не раньше — придут следующие.
4. `/settings` — выключить тип и проверить, что он больше не приходит. Заблокировать бота — после следующей попытки отправки в базе `can_message = false`.

## Управление

- Перетаскивание пальцем/мышью по полю — двигать карту.
- Щипок двумя пальцами / колесо мыши — масштаб.
- «Строить» — меню зданий с ценой, временем, лимитом; недоступные — серые с причиной, с замком, если нужна ратуша выше.
- Строку меню можно перетащить на поле (место подсвечивается зелёным/красным) или тапнуть и затем тапнуть по полю.
- Тап по зданию — панель: уровень, добыча, прочность, «Улучшить» (цена и время) и «Переместить».
- Тап по шахте/ферме со значком над ней — собрать накопленное.
- Слева внизу — занятые строители (1/2, 2/2).
- Здание появляется только после подтверждения сервером; при отказе показывается короткое сообщение.
